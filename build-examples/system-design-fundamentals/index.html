Master the Fundamentals

System design is the process of defining the architecture, components, and data for a system to satisfy specified requirements. It's the art of managing complexity and making informed tradeoffs.

In modern software engineering, system design is what separates a "coder" from an "architect." Whether you're preparing for technical interviews or building the next global platform, understanding how components interact at scale is essential.

Tradeoff Example

Imagine building a messaging app. You want users to see messages instantly (Low Latency), but you also want them to see the exact same history on all their devices (Strong Consistency). Achieving both at global scale is a classic system design challenge.

Key Takeaway

System design is rarely about finding the "best" solution, but rather the "right" solution for a specific set of constraints. Every decision involves a tradeoff: latency vs. consistency, cost vs. performance, or simplicity vs. features.

1. Scalability: Vertical vs. Horizontal

Scalability is the ability of a system to handle increased load. When a system reaches its limit, you have two primary ways to grow.

Vertical Scaling (Scaling Up)

Adding more power (CPU, RAM, SSD) to an existing server. It's simple and requires no architectural changes, but it has a hard ceiling and introduces a single point of failure.

Horizontal Scaling (Scaling Out)

Adding more servers to your pool. This is the foundation of modern distributed systems. It's virtually limitless but adds complexity in networking and data consistency.

Example

If your single database server is slow, upgrading it from 16GB to 128GB of RAM is Vertical Scaling. Spreading the data across ten identical 16GB servers is Horizontal Scaling.

Key Takeaway

Vertical scaling is great for low-traffic apps or small teams, but horizontal scaling is mandatory for high-availability, planet-scale systems.

2. Load Balancing

A Load Balancer (LB) acts as a traffic cop, distributing incoming network requests across a pool of backend servers. This prevents any single server from becoming a bottleneck and ensures high availability.

LBs operate at different layers: Layer 4 (Transport) looks at IP and port, while Layer 7 (Application) can inspect HTTP headers and cookies for more intelligent routing.

3. Caching

Caching is the process of storing copies of data in a temporary storage layer (the cache) so that future requests for that data can be served faster. It's the single most effective way to improve system performance.

Where to Cache?

  • Client-side: Browser caching for assets.
  • CDN: Edge caching for static and dynamic content.
  • Application: In-memory stores like Redis or Memcached.
  • Database: Built-in query result caches.

Eviction & Invalidation

Caches have limited space. LRU (Least Recently Used) is a popular policy that removes the oldest data first. TTL (Time to Live) ensures data eventually expires so the cache doesn't stay stale forever.

Example: Write-Through vs. Write-Back

In a Write-Through cache, data is written to the cache and the DB simultaneously. In Write-Back, data is written only to the cache and synced to the DB later (faster writes, but risk of data loss if the cache fails).

"There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton

Key Takeaway

Caching is a powerful tool but introduces complexity in keeping data consistent. Always define a clear eviction policy (like LRU) and expiration strategy (TTL).

4. Databases: SQL vs. NoSQL

Choosing a database is one of the most critical decisions in system design. The choice usually boils down to the structure of your data and how you need to query it.

Relational (SQL)

Structured data with fixed schemas. Great for complex joins and ACID compliance. Best for financial systems or applications with complex relationships. (e.g., PostgreSQL, MySQL).

Non-Relational (NoSQL)

Flexible schemas. Built for horizontal scale. Types include Document (MongoDB), Key-Value (Redis), Wide-Column (Cassandra), and Graph (Neo4j).

Indexing Basics

An index is a data structure (often a B-Tree) that improves the speed of data retrieval operations. While it makes reads faster, it slows down writes because the index must be updated every time data changes.

Example: SQL Schema

CREATE TABLE users (id INT PRIMARY KEY, email VARCHAR(255) UNIQUE);

This table uses a primary key index on id and a unique index on email for fast lookups.

Key Takeaway

Pick SQL when data integrity and complex relationships are paramount. Pick NoSQL when you have massive scale, unpredictable data structures, or need rapid development without schema migrations.

5. Replication

Replication involves keeping a copy of the same data on multiple machines. It's used to increase availability (if one node fails, others are ready) and decrease latency (serve data from the node closest to the user).

Replication Models

  • Leader-Follower: All writes go to the leader. Follower nodes pull updates for reads.
  • Multi-Leader: Multiple nodes accept writes. Complex to resolve conflicts.
  • Leaderless: Any node can accept reads/writes. Used in systems like DynamoDB or Cassandra.

Example: Replication Lag

If you update your profile on the Leader and immediately refresh, but the read hits a Follower that hasn't synced yet, you might see your old data. This is Eventual Consistency.

Key Takeaway

Replication is for Availability. It ensures that if one server dies, your data isn't lost and your system stays online.

6. Sharding / Partitioning

Sharding is the process of breaking up a large dataset into smaller, more manageable chunks (shards) and distributing them across multiple database servers.

Unlike replication, where every node has the same data, each shard contains a unique subset of the total data.

Partitioning Strategies

  • Range Based: Dividing data by a range of values (e.g., Users A-M in Shard 1, N-Z in Shard 2).
  • Hash Based: Applying a hash function to the key to determine the shard (distributes data more evenly).
  • Directory Based: A lookup service tracks which shard holds which data.

Sharding is for Scalability. It allows a database to handle more data and more traffic than a single machine ever could. Choosing the right Shard Key is the most critical decision.

7. CAP Theorem & Consistency

The CAP Theorem states that a distributed system can only provide two of the following three guarantees at the same time:

  • Consistency (C): Every read receives the most recent write or an error.
  • Availability (A): Every request receives a non-error response, without the guarantee that it contains the most recent write.
  • Partition Tolerance (P): The system continues to operate despite an arbitrary number of messages being dropped or delayed by the network.

Consistency Models

Beyond CAP, we have various models for how consistent we need our data to be:

  • Strong Consistency: After a write, any subsequent read will see that write.
  • Eventual Consistency: If no new writes are made, eventually all reads will return the same value.
  • Causal Consistency: Ensures that operations that are causally related are seen by all nodes in the same order.
  • Read-your-writes: A user will always see their own updates immediately.

CP vs. AP

In a network failure (Partition), you must choose: either shut down the system to ensure data is correct (CP), or keep serving requests even if the data might be stale (AP).

Key Takeaway

In a distributed world, Partition Tolerance (P) is not optional. Therefore, you are always choosing between Consistency (CP) and Availability (AP).

8. Message Queues & Async Processing

In a synchronous system, the user waits for the entire process to finish. Message Queues (MQ) allow for asynchronous processing: the application "drops a note" in the queue and moves on, while a background worker processes it later.

Core Concepts

  • Producer/Consumer: One component creates tasks; another (or many) executes them.
  • Backpressure: If the consumer is too slow, the system must slow down the producer or drop messages.
  • Retries & DLQ: Failed tasks are retried. If they keep failing, they go to a Dead Letter Queue (DLQ) for manual inspection.

Example: Video Upload

When you upload a video to YouTube, the web server saves the raw file and puts a "task" in a queue. A worker fleet picks up the task to transcode it into 1080p, 720p, etc. You don't have to wait for the transcoding to finish to get a "Success" message.

Key Takeaway

Queues decouple your system components. They handle spikes in traffic by buffering requests, allowing your backend to process them at a steady, sustainable pace.

9. CDNs & Geographic Distribution

A Content Delivery Network (CDN) is a globally distributed network of proxy servers. Its goal is to provide high availability and performance by distributing content from locations "closer" to the end user.

Beyond static assets (images, CSS, JS), modern CDNs also handle Edge Computing and Security (DDoS protection, WAF).

Example

If your server is in New York and a user is in Tokyo, a round-trip request takes ~200ms just for the light to travel. A CDN node in Tokyo can serve that same file in under 10ms.

How to Practice

Theory is a start, but system design is a muscle that needs exercise. Try designing these systems on paper or a whiteboard:

  • URL Shortener (Bit.ly): Focus on read/write ratios and hashing.
  • Twitter Feed: Focus on fan-out (how to show one tweet to millions).
  • Uber: Focus on geospatial indexing and real-time updates.
  • Web Crawler: Focus on distributed workers and deduplication.

For each design, always ask: "What happens if I have 10x the users? 100x? Where is the single point of failure?"
